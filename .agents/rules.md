# Google - The Gemma 4 Developer Agent Competition: Rules & Technical Specification

> **Official Competition:** [Google - The Gemma 4 Developer Agent Competition (Kaggle)](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview)  
> **Host:** Google DeepMind & Kaggle  
> **Core Objective:** Build, post-train, and configure an autonomous software engineering developer agent powered by the open-weight **Gemma 4** model family to resolve real-world software repository issues in an offline, sandboxed environment.

---

## 1. Executive Summary & Competition Paradigm

Unlike conventional machine learning competitions where competitors submit flat tabular predictions (`submission.csv`), this competition requires submitting an **autonomous coding agent package (`submission.zip`)**. The agent is evaluated against real-world GitHub issues (resembling benchmarks like SWE-bench), where it must independently inspect repository codebases, localize bugs, synthesize patches, and execute unit tests.

### Key Evaluation Track:
1. **The Prediction / Agent Competition (Primary):** Leaderboard ranking based on the functional pass rate of patches generated by the agent across hidden test repositories.
2. **The Companion Paper Track:** Formal research writeup detailing agent architecture, fine-tuning methodologies, test-time compute scaling, and empirical findings.

---

## 2. Evaluation Mechanics & Scoring Metric

* **Primary Metric:** **Pass@1 Resolution Rate**
  $$\text{Score} = \frac{\text{Number of Resolved Evaluation Tasks}}{\text{Total Evaluation Tasks}} \times 100\%$$
* **Task Lifecycle:**
  1. The harness loads an issue from `tasks.jsonl` (contains `task_id`, `repo`, `base_commit`, `issue_description`).
  2. The agent is initialized inside an isolated container clone of the repository at the specified commit.
  3. The agent interacts with the sandbox environment via registered tools (running commands, reading files, editing code).
  4. The agent concludes by invoking `submit_patch`.
  5. The harness applies the generated git patch to a clean repository clone and executes pre-defined validation unit tests.
  6. The task is marked strictly **PASS** (1) or **FAIL** (0). No partial credit is awarded.

## 3. Sandboxed Architecture & ADK Security Constraints

The competition runtime uses **Google ADK (Agent Development Kit)** with a sandboxed YAML compiler (`adk-submission` / `compile_submission`).

### Strict Declarative-Only Security Model
* **NO Arbitrary Python Entrypoints:** Custom `agent.py`, `agent_fn`, or dynamic code execution via `importlib` are **strictly forbidden** in submissions. Any custom Python script entrypoint will fail submission validation.
* **Declarative Configuration:** Agents, sub-agents, tool bindings, system prompts, skills, and generation parameters must be statically declared via YAML and Markdown files.
* **Root `agent.yaml` Requirement:** The root of `submission.zip` **must** contain `agent.yaml`.

### Closed Host Registries
During evaluation, all declarations in `agent.yaml` are verified against sealed host registries:
1. **`ToolRegistry`:** Only registered environment primitives are available:
   - `run_command`: Execute non-destructive shell commands in the repository sandbox.
   - `read_file`: Inspect file contents with line offset/range options.
   - `edit_file`: Contiguous string replacement or line edits.
   - `write_file`: Create or overwrite files.
   - `get_status`: Git status and diff viewer.
   - `code_graph_search`: AST / symbol navigation across repository files.
   - `submit_patch`: Finalizes the task and registers the output git diff.
   - *Custom functionality:* Must be structured using the **Agent-as-a-Tool** pattern (`agent_tool`), nesting specialized sub-agents defined in YAML.
2. **`ModelRegistry`:** Only permitted Gemma 4 variants:
   - `gemma-4-31b-it-qat-w4a16-ct` (Quantization-Aware Training, 4-bit weights / 16-bit activations)
   - `gemma-4-26b-moe` (Mixture of Experts)
   - `gemma-4-12b-it-qat-w4a16-ct` (Workstation/Consumer tier)
   - `gemma-4-e4b` / `gemma-4-e2b` (Constrained edge variants)
3. **Model Consistency Rule:**
   - **All agents and sub-agents in a single submission MUST target the identical base model variant.** Mixing base models (e.g. 31B for root and 12B for sub-agent) causes compilation rejection.

## 4. Kaggle Platform Constraints & Runtime Limits

| Parameter | Constraint | Operational Guidance |
| :--- | :--- | :--- |
| **Internet Access** | **Strictly Disabled (Offline)** | Pre-install all packages via offline wheelhouses (`gemma-4-developer-agent-wheelhouse`). No `pip install` from PyPI during evaluation. |
| **Submission Format** | `submission.zip` | Must contain `agent.yaml` at root. Max uncompressed size limits apply to LoRA checkpoints. |
| **Model Weights** | Kaggle Model Datasets | Base Gemma 4 weights must be loaded from Kaggle Models or pre-packaged local paths; cannot be downloaded during inference. |
| **Active Runtime Limit** | Strict Wall-clock Budget | Up to ~9–12 hours total for complete evaluation across all tasks. Per-task execution budget must be guarded by timeout or max turns. |
| **Inference Backend** | Local vLLM Server + LiteLLM | Model serving runs locally via vLLM. High-throughput tensor parallelism and paged attention are mandatory to prevent Out-Of-Memory (OOM). |
| **LoRA Adapters** | Supported | LoRA adapter weights must be declared in `agent.yaml` and loaded via vLLM `--lora-modules` or PEFT. |

## 6. Winning Technical Playbook

To achieve top-tier performance on the leaderboard, adhere to the following principles:

### A. Localization Before Patching (Separation of Concerns)
* The biggest failure mode of coding LLMs is "premature patching" (editing without understanding root cause).
* Decompose the agent architecture into a 3-stage loop:
  1. **Phase 1: Diagnosis & Localization:** Use `code_graph_search` and `read_file` to pinpoint the offending file and line range.
  2. **Phase 2: Reproduction & Synthesis:** Replicate the failing behavior with a minimal test or understand the reproduction steps in the issue. Draft surgical changes using `edit_file`.
  3. **Phase 3: Verification & Regression Check:** Run repository test suites via `run_command` (`pytest`, `unittest`). Never call `submit_patch` until tests pass!

### B. High-Fidelity Fine-Tuning (SFT + DPO/GRPO)
* **SFT (Supervised Fine-Tuning):** Train Gemma 4 on clean trajectories of successful issue resolutions (SWE-bench Verified / SWE-bench Lite). Format training data strictly using Gemma 4 chat and tool-calling special tokens (`<start_of_turn>`, `<end_of_turn>`).
* **RL / DPO:** Penalize tool call hallucinations, invalid file paths, syntax errors, and non-terminating tool loops.

### C. Guardrails Against Budget Exhaustion
* Implement strict step limits per task (e.g., maximum 25 turns per issue).
* If after 15 turns no patch is found, fall back to the highest-confidence localized candidate rather than exhausting the global runtime budget.

## 7. Development & Iteration Workflow Rules

1. **Never commit untested `agent.yaml`:** Always validate against `compile_submission()` locally before uploading.
2. **Log Every Experiment:** Every fine-tuning run or agent prompt modification must have an entry in `experiments/` documenting hypothesis, config, local pass rate, errors, and verdict.
3. **Offline First:** Ensure all notebook code runs 100% offline with cached dependencies.
